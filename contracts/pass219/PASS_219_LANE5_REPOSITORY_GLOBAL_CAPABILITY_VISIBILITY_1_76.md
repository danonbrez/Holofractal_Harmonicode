## Global visibility invariant

For every repository object or repository reference admitted to this discovery projection:

Discovered(x) => Lane5Visible(x)

An unresolved state, classification marker, open PR, branch-only implementation, demo, example, reference, candidate_only, enabled=false, ready=false, adapter hint, configuration hint, or deprecation hint is preserved as metadata and does not by itself remove the object from Lane 5 visibility.

Unresolved(x) => Lane5Visible(x) AND ClosureState(x)=UNRESOLVED

No agent or discovery pass may convert uncertainty into invisibility.

## Visibility is not authority

The successor preserves five independent concepts:

VISIBLE
COMPOSITION-ELIGIBLE
RUNTIME-VALIDATED
CANONICALLY-ADMITTED
MUTATION-AUTHORIZED

They are not interchangeable.

A source capability may be visible and composition-eligible while still requiring runtime validation. The inability to bypass Linux, services, the Pass 219 C++ RNA membrane, PQC boundaries, or signed environmental VM81 admission is not evidence that the capability is a demo or non-executable. It is the expected HHS execution boundary.

The projection itself has no execution or canonical mutation authority.

## Fully implemented capability rule

A repository capability that has implementation evidence is not automatically downgraded to demo, reference, non-executable, needs adapter, needs configuration, or not ready merely because direct kernel/service bypass is prohibited.

Adapter/configuration requirements are factual interface/dependency states. If such strings are discovered, 1.76 records them as classification hints until a governing contract or runtime validation establishes the actual requirement.

## Repository objects

1.76 binds every tracked content-bound repository file already present in the Hash216 repository dependency graph into a visibility record.

Each record preserves repository path, source file Hash216, Git blob identity, language/disposition/origin, object class, classification markers, Lane 5 visibility, execution/composition eligibility, runtime-validation requirement, explicit zero direct-kernel/direct-service bypass authority, explicit zero canonical mutation/mint/persistence authority, and a domain-separated 216-character identity.

No tracked object is removed because of classification markers.

## Branch and pull-request evidence

1.76 accepts repository-reference inventory records for branch heads and pull-request heads.

Reference discovery is static. Branch/PR code is not imported or executed merely to make it visible.

A reference record may preserve ref kind/name, head SHA, pull-request number, draft state, validation state, merge state, and changed paths. Unresolved reference state remains visible and carries no canonical authority.

## Merged-green evidence

Where workflow/check provenance is available, a successfully validated merged PR should be represented as inherited integration evidence. Later dependency-relevant changes may reopen validation, but they do not erase the historical fact that the capability previously integrated successfully.

GreenMerged(c,t0) AND NOT TouchedDependencies(c,t0,t1) => IntegrationEvidenceInherited(c,t1)

This contract does not invent green status when check provenance is absent.
