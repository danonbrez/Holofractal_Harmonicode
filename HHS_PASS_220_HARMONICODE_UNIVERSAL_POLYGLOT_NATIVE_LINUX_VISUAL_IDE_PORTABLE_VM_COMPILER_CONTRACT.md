# 6. Product thesis and non-reinvention law

The governing product law is:

> **Adopt what the software community has already solved; make HARMONICODE-native capabilities solve the remaining limitations.**

Where mature standards and ecosystems exist, Pass 220 SHOULD integrate them. HARMONICODE SHALL NOT create proprietary replacements merely to duplicate mature language servers, debuggers, package managers, source-control systems, graphics APIs, audio frameworks, desktop conventions, container formats, or project structures.

A HARMONICODE-native replacement MAY be introduced only when an established interface cannot express a binding capability, cannot preserve an HHS invariant, fails a measured performance/determinism requirement, or a stricter security/authority boundary is required. Compatibility SHOULD remain available wherever possible.

A contraction SHALL identify descendants no longer admissible. They may remain historical under the old contract, migrate, repair, branch, quarantine, or block promotion, but SHALL NOT disappear silently.

# 43. Authenticated non-fungible computational objects

Pass 220 SHALL expose the localized VM81/Hash72/Hash216 identity model through an object-oriented abstraction called an **Authenticated Non-Fungible Computational Object**.

“Non-fungible” here means stable computational identity. It does not require blockchain marketplaces, token trading, speculative economics, or public-chain deployment.

An object SHALL be capable of carrying stable identity, declared type, state identity, class/interface identity, properties, methods, local constraints, capabilities, dependency edges, modality facets, permissions, forward/inverse witnesses, serialization/reconstruction contract, Hash216 ancestry, VM81 execution reference, and VM5184 hydration reference.

# 45. Hyperobject model

The same typed object MAY simultaneously participate in multiple scene, physics, network, audio, AI, persistence, build, scientific, or organizational hyperobjects.

This SHALL prevent integration-specific type explosion.

# 46. Ordered relation safety

`BEFORE` and `AFTER` participate in dependency scheduling.

Cycles in a declared acyclic order SHALL be rejected with an intelligible diagnostic.

Recursive/fixed-point cycles MAY exist only under an explicit contract defining entry state, iteration rule, termination/bounded execution, convergence/closure rule, and rollback.

Containment ownership cycles SHALL be rejected unless explicitly non-owning/reference semantics are used.

# 144. Implementation phases

Pass 220 SHOULD use bounded restartable iterations:

## Iteration 1 — authoritative inventory and standards freeze
Record terminal Pass 219 base, deep scan current GUI/API/CLI/languages/toolchains, freeze standards registry, migration map, and performance baseline requirements.

## Iteration 2 — common workspace/action/receipt nucleus
Implement common workspace graph, action schema, receipt schema, common CLI/API dispatch, and dependency-scoped history.

## Iteration 3 — native Linux GUI shell
Implement XDG/Desktop Entry/Wayland-integrated native application with workspace/editor/terminal/problems/output and explicit degraded behavior.

## Iteration 4 — polyglot bootstrap and ecosystem integration
Implement Git/local/GitHub import, toolchain/package discovery, build/run/test discovery, and trust model.

## Iteration 5 — language services/debug/test
Integrate LSP, DAP, test federation, diagnostics, and source mappings.

## Iteration 6 — plugins and developer customization
Implement plugin SDK/manifest, libraries, macros, workflows, developer profile, and permissions.

## Iteration 7 — history, impact, contract evolution, hyperobjects
Implement history UI, semantic undo, impact cones, contract overlays, and hyperobject graph.

## Iteration 8 — profiler/optimization and portable compiler
Implement common profiler, HHS optimization metrics, HPM, multi-target lowering, standard/enhanced profiles.

## Iteration 9 — game/scientific/hardware multimodality
Implement standards adapters and bounded scientific/hardware/cross-modality fixtures.

## Iteration 10 — agent swarms and enterprise governance
Implement discovery API, work claims, ownership/conflict, requirements, approvals/policy, and supply chain.

## Iteration 11 — self-hosting and portability hardening
Implement bootstrap/self-hosting evidence, architecture matrix, remote targets, packaging, and reproducibility hardening.

## Iteration 12 — zero-briefing alpha and terminal closure
Run independent developer study, repair discoverability blockers, performance profile, dependency-scoped final validation, merge, exact-head verify, and close.

Iteration count MAY change if dependency boundaries justify it. Scope SHALL not silently disappear.
