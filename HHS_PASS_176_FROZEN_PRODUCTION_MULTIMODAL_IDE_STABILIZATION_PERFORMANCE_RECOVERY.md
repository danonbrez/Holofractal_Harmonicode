# 2. Normative language

The terms **SHALL**, **SHALL NOT**, **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are normative.

This document authorizes Pass 176 implementation after the activation gate is satisfied. It does not itself prove that browser errors, slowdowns, freezes, memory leaks, initialization races, mobile defects, deployment failures, or workflow defects have been removed.

# 3. Append-only inheritance

Pass 176 SHALL inherit every compatible repository-visible contract, implementation, test, schema, API, ABI, compiler surface, Visual IDE workflow, deployment rule, correction, evidence record, and receipt through Pass 175 as a minimum foundation.

Pass 176 SHALL preserve, without semantic weakening:

- HARMONICODE source authority;
- exact operand order, grouping, lexical width, leading zero, and circuit-token identity;
- VM81 as the sole canonical state-transition authority;
- Hash72 as the single ordered authoritative commit stream;
- Hash216 as the inherited instruction, object, operation, and provenance indexing fabric;
- Pass 174 canonical system-image identity;
- Pass 175 VM5184 × G243 instruction hydration and execution hierarchy;
- public API gateway authority;
- multimodal ingress and egress governance;
- restartability, bounded closure, incremental Git history, and authoritative-main delivery;
- interface primacy and human-readable workflow requirements;
- all pre-pass and numbered-pass lineage visible through the integrated repository-history subsystem.

Pass 176 SHALL NOT renumber Pass 175, absorb the Pass 175 kernel into the frontend, create a second runtime authority, or represent frontend state as canonical machine state.

# 4. Governing distinction

\[
\boxed{\text{frozen interface identity}\neq\text{frozen implementation defects}}
\]

The accepted interface configuration SHALL be frozen as the visual and interaction baseline. Internal source, scheduling, caching, rendering, resource ownership, event wiring, data loading, error handling, and transport behavior MAY be repaired or replaced when the resulting interface preserves the accepted product identity and improves verified reliability.

A repair that removes or hides a required capability is not stabilization.

# 7. Prohibited substitutions

Pass 176 SHALL NOT replace the frozen IDE with:

- a status dashboard;
- a landing page;
- a collection of disconnected cards;
- a static HTML demonstration;
- a raw JSON viewer;
- a receipt-validation page;
- a runtime-health page alone;
- an iframe that delegates the product to an unrelated external editor;
- an assistant-only chat surface;
- a terminal-only environment;
- a visual shell whose controls do not execute real backend workflows.

The diagnostic console MAY remain available, but it SHALL NOT displace the full IDE from the principal route.

# 8. Required result

Pass 176 SHALL deliver a production IDE that:

1. retains the accepted visual structure and theme;
2. reaches an interactive development state deterministically;
3. creates, opens, edits, saves, imports, previews, runs, compiles, and exports real projects;
4. keeps the natural-language assistant continuously discoverable and usable;
5. performs heavy work without indefinite main-thread blockage;
6. presents bounded progress and cancellation for long-running operations;
7. preserves unsaved work through recoverable frontend failures;
8. releases preview, media, worker, timer, object-URL, stream, and event resources;
9. prevents duplicate initialization and duplicate event dispatch;
10. remains usable during lazy registry, history, receipt, snapshot, and diagnostic loading;
11. provides safe click, touch, keyboard, pointer, drag, resize, and scroll behavior;
12. makes errors actionable and recoverable rather than freezing silently;
13. preserves backend and VM81 authority exactly;
14. passes desktop and mobile browser acceptance against the actual production entrypoint;
15. closes implementation on authoritative `main` with deployment verification.

# 9. Startup state machine

IDE boot SHALL be explicit, observable, and idempotent.

The minimum state machine is:

```text
DOCUMENT_READY
→ STATIC_THEME_READY
→ CORE_WORKSPACE_READY
→ PROJECT_STATE_RESTORED
→ EDITOR_READY
→ PREVIEW_READY
→ ASSISTANT_READY
→ BACKEND_CAPABILITY_CHECKED
→ OPTIONAL_REGISTRY_HISTORY_DIAGNOSTICS_LOADING
→ INTERACTIVE
```

Failure of an optional registry, history, receipt, benchmark, or diagnostic service SHALL NOT prevent the editor, file tree, project creation, assistant shell, local preview, or recoverable project state from becoming interactive.

Every initialization unit SHALL be safe to call more than once. Duplicate listeners, duplicate observers, duplicate timers, duplicate WebSocket clients, duplicate workers, and duplicate boot requests are forbidden.

# 10. Main-thread responsiveness

Pass 176 SHALL identify and bound all expensive browser work, including:

- syntax rendering;
- large file-tree reconciliation;
- registry hydration;
- pass-history indexing;
- 5,184-cell visualization;
- Hash216 lane rendering;
- preview document assembly;
- CRC and ZIP generation;
- media decoding and encoding;
- source hashing;
- compiler artifact formatting;
- large terminal and receipt rendering;
- search and filter operations.

Work that can exceed one rendering frame SHOULD be chunked, streamed, deferred, virtualized, or moved to a Web Worker. Canonical decisions SHALL remain in inherited backend authorities.

No operation may leave the interface without a visible state transition, progress indication, timeout boundary, cancellation path where cancellation is safe, or recovery action.

# 11. Performance profiles

The inherited profiles `MOBILE_SAFE`, `BALANCED`, `DESKTOP_HIGH`, `HIGH_REFRESH`, and `DIAGNOSTIC` SHALL control presentation and scheduling cost without altering canonical semantics.

Profiles MAY govern:

- animation refresh rate;
- preview resolution;
- registry page size;
- file-tree virtualization window;
- terminal retention length;
- 3D scene complexity;
- snapshot sampling density;
- background refresh frequency;
- worker concurrency;
- media preview quality;
- diagnostic verbosity.

A lower-cost profile SHALL NOT remove project data, alter compiler output, skip VM81 admission, or change receipt identity.

# 12. Error elimination

Terminal Pass 176 browser evidence SHALL show no unexplained:

- uncaught exception;
- unhandled promise rejection;
- console error;
- static-asset 404;
- API route 404 for a required workflow;
- infinite retry loop;
- unresolved loading state;
- detached DOM write;
- null-element event binding;
- duplicate action execution;
- stale project overwrite;
- preview source corruption;
- leaked media capture;
- leaked audio context;
- leaked animation frame;
- leaked object URL;
- failed export represented as successful.

Known third-party warnings MAY be accepted only when documented, bounded, nonfunctional, and accompanied by evidence that they do not hide a repository defect.

# 13. Project-state integrity

Project identity SHALL be explicit and versioned. The frontend SHALL preserve at least:

- project identifier and display name;
- template or origin identity;
- ordered file paths;
- file content and binary encoding;
- active file and open tabs;
- dirty state;
- last durable save point;
- selected build and compiler targets;
- preview entrypoint;
- workflow state;
- latest successful artifacts;
- recoverable error state.

Switching projects SHALL load the destination project before editor synchronization. Source from one project SHALL NOT overwrite another project during activation, restoration, preview, build, or autosave.

Autosave SHALL be debounced, atomic at the project-record level, and recoverable. It SHALL NOT claim backend or VM81 durability unless the authoritative backend confirms it.

# 14. File and folder operations

File creation, renaming, movement, deletion, folder ingress, and drag-and-drop SHALL be human-safe.

Required protections include:

- path normalization;
- traversal rejection;
- collision detection;
- non-destructive default behavior;
- explicit replacement confirmation;
- unique-name generation when requested;
- binary/text distinction;
- size and count bounds;
- visible skipped-file reporting;
- reversible or recoverable deletion where feasible;
- preservation of relative folder paths;
- no silent flattening of distinct files;
- no silent overwrite from drag operations.

A pointer movement below the configured drag threshold SHALL remain a click and SHALL NOT reorder or move content.

# 15. Click, touch, drag, resize, and scroll safety

Every interactive surface SHALL define its pointer ownership and cancellation behavior.

At minimum:

- dragging a file SHALL not select text unpredictably;
- resizing a pane SHALL not activate underlying controls;
- scrolling a file tree SHALL not start a drag;
- pinch gestures in the 3D or preview surface SHALL not resize unrelated panes;
- touch controls SHALL have adequate targets and visible pressed states;
- pointer capture SHALL be released on completion, cancellation, blur, route change, and error;
- keyboard focus SHALL remain visible and recoverable;
- Escape SHALL cancel transient menus, drags, and dialogs where safe;
- destructive actions SHALL require explicit intent;
- reordering tabs or files SHALL not mutate source contents.

# 16. Editor reliability

The editor SHALL provide stable source editing for text, code, configuration, HARMONICODE, Markdown, structured data, and other registered textual modes.

It SHALL preserve:

- exact source bytes where canonical transport requires them;
- leading zeros and lexical widths;
- newline form when declared significant;
- tab and space identity where required;
- Unicode source;
- undo and redo history within bounded memory;
- cursor and selection state;
- line-number synchronization;
- safe large-file fallback behavior.

Syntax presentation SHALL remain nonauthoritative and SHALL NOT rewrite canonical source.

# 17. Natural-language assistant

The natural-language assistant SHALL be a persistent IDE capability, not a separate demonstration page.

The assistant SHALL:

- be reachable from desktop and mobile controls;
- preserve a visible status state;
- operate in a drawer, pane, or workspace that does not destroy editor state;
- receive the active project, selected file, cursor selection, build status, preview status, and error context only through explicit governed context envelopes;
- propose or apply file changes with a reviewable diff or equivalent human-readable representation;
- invoke real project, compiler, test, preview, and export workflows through public authorized surfaces;
- distinguish suggestions from executed mutations;
- preserve conversation state across pane changes;
- fail visibly and recoverably when the model provider is unavailable;
- avoid blocking basic local editing and preview when remote inference is unavailable.

No assistant response may bypass VM81, compiler, file, deployment, or security authority.

# 18. Runtime registry and repository lineage

The runtime registry and repository-history workbench SHALL remain available but SHALL load incrementally.

Requirements include:

- pagination or virtualization;
- bounded search;
- cancellation of superseded queries;
- cached immutable pass and commit metadata;
- no full-history fetch on every render;
- no registry refresh that resets editor state;
- pass-contract, evidence, status, ancestry, supersession, and commit-lineage inspection;
- clear distinction between contracts, implementations, evidence, receipts, and terminal closure;
- read-only treatment unless a separately authorized repository workflow is invoked.

Repository history SHALL support the IDE; it SHALL NOT replace application development as the principal surface.

# 19. Preview execution

Application and media preview SHALL be isolated, deterministic enough for testing, and disposable.

The preview manager SHALL:

- build from the currently selected project version;
- resolve project-local HTML, CSS, JavaScript, image, audio, video, document, and registered asset references;
- use a sandbox appropriate to the requested capability;
- expose preview console output and runtime faults;
- terminate prior animation frames, timers, event bridges, workers, streams, object URLs, and media contexts when rebuilding;
- prevent stale preview messages from mutating the current project;
- provide reload, stop, open, and recover actions;
- preserve exported standalone behavior even when the internal preview sandbox restricts storage or device APIs.

A preview fault SHALL NOT freeze the parent IDE.

# 20. Multimodal ingress

Pass 176 SHALL stabilize ingress for at least:

- source code;
- text and Markdown;
- JSON, JSONL, CSV, XML, and registered structured formats;
- PDF and document sources;
- raster and vector images;
- audio;
- video;
- binary assets;
- project folders;
- existing HHS manifests, receipts, specifications, and artifacts.

Ingress SHALL retain original bytes, media type, path, size, source identity, and derived-preview identity. Derived thumbnails, waveforms, transcripts, frames, indexes, or embeddings SHALL not replace original source authority.

# 21. Compiler and VM workflow preservation

The simple workflow MAY use plain-language actions such as:

```text
New Application
Add Files
Build & Preview
Test
Compile
Export
```

The expert workflow SHALL retain inspectable stages for:

```text
Ingress
→ Hash216 index
→ 5,184-bit snapshot
→ exact interpretation
→ target compilation
→ VM81 execution
→ replay
→ governed egress
```

Simple controls SHALL call the same authorized services as expert controls. No simplified workflow may create an alternate compiler, state authority, receipt stream, or ungoverned execution path.

# 22. Build and export stability

Build, compiler, and export operations SHALL be represented as bounded jobs with explicit identity.

Each job SHALL expose:

- project version;
- source root;
- requested targets;
- stage;
- progress where measurable;
- start and completion times;
- cancellation capability where safe;
- warnings and errors;
- produced artifact identities;
- authoritative backend receipts where applicable.

ZIP creation SHALL reject duplicate or unsafe paths, preserve UTF-8 names, validate CRC and directory structure, and avoid blocking the UI for large projects. The deployable browser application and the full HHS project archive SHALL remain distinct export products.

# 23. Network, timeout, retry, and offline behavior

Every required request SHALL have a bounded timeout and visible failure state.

Retries SHALL be:

- finite;
- idempotency-aware;
- cancellable;
- jittered where appropriate;
- prevented from duplicating mutations;
- prevented from resetting newer user state.

Local project editing, supported local preview, and recoverable project storage SHOULD remain usable during backend or network interruption. Operations requiring VM81, compilation, assistant inference, durable storage, or deployment SHALL disclose their unavailable status rather than simulate success.

# 24. Concurrency and stale-response control

Every asynchronous operation that can be superseded SHALL carry a request, project, file, and generation identity.

A response SHALL be ignored or reconciled when its identity no longer matches the active generation. This applies to:

- project loading;
- file reads;
- preview builds;
- registry searches;
- pass-history queries;
- assistant turns;
- compilation;
- tests;
- media processing;
- exports;
- runtime snapshots.

Completion order SHALL NOT silently determine user-visible authority.

# 25. Resource lifecycle

Pass 176 SHALL inventory and govern:

- DOM listeners;
- observers;
- timers;
- animation frames;
- Web Workers;
- WebSockets;
- fetch controllers;
- object URLs;
- file handles;
- audio contexts and nodes;
- media streams and tracks;
- canvas and WebGL resources;
- preview frames;
- caches;
- terminal buffers;
- retained project snapshots.

Every resource owner SHALL provide deterministic disposal. Repeated project creation, preview rebuilding, assistant opening, registry refresh, and route switching SHALL not cause unbounded resource growth.

# 26. Mobile and constrained-device operation

The `MOBILE_SAFE` profile SHALL prioritize editing, assistant access, project navigation, preview, and export over decorative rendering.

Mobile acceptance SHALL cover:

- portrait and landscape layout;
- virtual keyboard appearance and dismissal;
- safe-area insets;
- file selection and content URI handling where supported;
- touch drag thresholds;
- pane switching without state loss;
- assistant access;
- preview controls;
- long-file scrolling;
- download and share behavior supported by the browser;
- recovery after backgrounding and return.
