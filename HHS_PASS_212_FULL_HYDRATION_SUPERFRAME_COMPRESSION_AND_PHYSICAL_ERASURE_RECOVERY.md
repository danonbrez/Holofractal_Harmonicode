## Corrected information envelope

The Pass 210 frame is a local recovery leaf. It is not the total hydration capacity.

```text
local address frame        81 × 64 = 5,184 bits
control projections        243
ordered lane/magnitude     8 × 5 = 40
full hydration             5,184 × 243 × 40
                           = 50,388,480 bits
                           = 6,298,560 bytes
local frame count          243 × 40 = 9,720
```

The canonical full-state address is:

```text
h = ((lane × 243 + control) × 5,184) + local_cell
```

where `lane ∈ [0,39]`, `control ∈ [0,242]`, and `local_cell ∈ [0,5183]`.

## Full-state compression

Each local leaf retains the Pass 210 affine recurrence:

```text
a[n] = (a[n-1] + a[n-2] - 1) mod 2
```

A leaf is therefore generated by two seed bits. Across all 9,720 leaves, the complete strict-domain seed is:

```text
9,720 × 2 = 19,440 bits = 2,430 bytes
```

Pass 212 stores those seeds once for the full hydration and records exact sparse XOR exceptions as strictly increasing global bit positions. It claims compression only when the resulting binary payload is smaller than the 6,298,560-byte raw state.

The frozen pure-domain vector compresses the complete 50,388,480-bit hydration to a 2,473-byte payload. Including two physical parity shards, the independently recoverable stored representation is 3,769 bytes. This is a measured full-state ratio of approximately `2546.930853:1` for that declared lattice domain.

A vector with 4,096 exact exceptions produces a 10,665-byte payload and 11,961 protected bytes, approximately `590.582278:1` before counting external filesystem/container overhead.

Arbitrary high-entropy states use a 6,298,560-byte raw fallback. They remain fully protected but are not described as compressed.

## Physical recovery

Hashes identify damage but do not reconstruct missing bytes. Pass 212 therefore persists real parity bytes.

Encoded payload bytes are divided into ordered 648-byte data shards. Each stripe contains at most 243 data shards and two GF(256) parity shards using primitive polynomial `0x11d`:

```text
P0 = XOR(data[0..n-1])
P1 = Σ (index+1) × data[index] over GF(256)
```

The runtime reconstructs any two missing physical shards in a stripe, including:

- two data shards;
- one data shard and either parity shard;
- both parity shards.

Three missing shards in one stripe are rejected as outside the declared erasure budget.

For an arbitrary uncompressed full hydration, the exact materialized layout is:

```text
9,720 data shards × 648 bytes = 6,298,560 bytes
40 stripes × 2 parity shards  =    51,840 bytes
protected total               = 6,350,400 bytes
```

That is approximately 0.823% physical parity overhead while permitting two independent losses in every lane stripe.

## Integrity hierarchy

Decode and recovery proceed in this order:

1. package schema, counts, and ordered shard metadata;
2. surviving physical data/parity Hash216 identities;
3. GF(256) reconstruction of missing bytes;
4. reconstructed shard Hash216 identities;
5. compressed descriptor parsing or raw fallback admission;
6. full 50,388,480-bit hydration regeneration;
7. state Hash216, 40 lane roots, and full hydration root;
8. package root and deterministic Hash72 receipt.

A missing shard is therefore reconstructed from surviving information rather than accepted because a hash still exists.
