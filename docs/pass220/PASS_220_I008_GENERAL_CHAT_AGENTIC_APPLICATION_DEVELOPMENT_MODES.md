# Pass 220 I008 — General Chat + Agentic Application Development Assistant Modes

Status: IMPLEMENTED CHECKPOINT / DEPENDENCY-SCOPED CI PENDING / NO AUTHORITY WIDENING

## 1. Product requirement

The production/native assistant is not restricted to a developer-agent role.

It exposes three user-selected operating modes:

```text
GENERAL_CHAT
AGENTIC_APPLICATION_DEVELOPMENT
BOTH
```

The mode is a language-generation/tool-routing policy. It does not change canonical VM81, Hash72, Hash216, filesystem, repository, or deployment authority.

## 2. General Chat

`GENERAL_CHAT` is an ordinary natural-language prompt/response mode.

The model receives:

```text
HHS_ASSISTANT_MODE=GENERAL_CHAT
```

and is instructed to behave as a normal conversational assistant.

In this mode:

- default HHS runtime/repository developer tools are removed from the provider request;
- the native provider does not auto-search the repository;
- ordinary questions remain in the prompt-response generation path;
- custom system instructions remain active;
- conversational history remains active;
- governed provider receipts/result ingress remain active;
- no direct runtime mutation authority is added.

This separates general conversation from application-development automation instead of treating every natural-language prompt as a repository task.

## 3. Agentic Application Development

`AGENTIC_APPLICATION_DEVELOPMENT` focuses the assistant on:

- application development;
- code;
- workspace operations;
- runtime diagnostics;
- testing;
- build/compile workflows;
- deployment;
- repository/source inspection;
- API/server/frontend/backend tasks.

Governed HHS assistant tools are available in this mode.

The native provider only activates repository retrieval when the prompt contains actual development intent. Unrelated general conversation is not silently converted into repository search; it receives a mode-bound response directing the user to General chat or Both.

Existing tool authority remains unchanged: the currently registered HHS assistant API tools are read-only and Hash72 witnessed. Any later mutating application-development operation must continue through its separate governed/user-authorized workflow.

## 4. Both

`BOTH` is the default compatibility mode.

It provides one assistant surface for:

```text
ordinary conversation
+
explicit governed application-development work
```

The model sees governed development tools, but the mode instruction explicitly forbids forcing developer tooling into unrelated general conversation.

The native HHS provider adds an independent intent membrane:

```text
ordinary conversational prompt
→ no automatic repository search
→ natural-language response

explicit code/repo/runtime/build/test/deploy prompt
→ governed development tool selection may occur
→ evidence is summarized conversationally
```

This keeps a single continuous assistant thread without making every prompt agentic.

## 5. Native prompt-response cycle

The repository-native provider now records explicit support for:

```text
general_chat_prompt_response_supported = true
agentic_application_development_supported = true
combined_mode_supported = true
```

Its mode is recovered from the system-message marker generated by the assistant service.

For General chat and ordinary Both-mode conversation, the native provider can complete without any HHS API tool round. It continues to use the installed native language surfaces, including the Pass 166 language memory and Pass 151 bounded semantic reasoning, while returning an OpenAI/LiteRT-compatible chat-completion envelope.

The native trace records:

```text
assistant_mode
general_chat_prompt_response_cycle
tool_receipt_count
runtime_mutation_admitted = false
```

The external/local Gemma/LiteRT provider uses the same mode-specific system instructions and request boundary.

## 6. Mode-specific tool membrane

The governed LiteRT tool wrapper distinguishes:

```text
tools is None
→ inherited default governed HHS tools

tools == []
→ intentionally no tools

tools supplied
→ inherited default tools + supplied compatible tools
```

The HHS API assistant therefore maps:

```text
GENERAL_CHAT
→ []

AGENTIC_APPLICATION_DEVELOPMENT
→ governed default tool surface

BOTH
→ governed default tool surface
```

General chat cannot accidentally regain the default HHS developer tool registry because an empty tool list now has explicit semantics.

## 7. System-instruction ordering

Provider system input is composed in this order:

```text
1. inherited governed HHS authority instruction
2. selected assistant-mode instruction
3. optional user custom system instructions
4. conversation history
```

User custom instructions therefore remain customizable but cannot replace the selected mode or inherited HHS authority boundary.

## 8. API

The assistant request schema now carries:

```text
assistant_mode: str = "BOTH"
```

through:

- `POST /api/assistant/chat`;
- `POST /api/assistant/threads/{thread_id}/messages`;
- `/api/assistant/ws/{thread_id}`.

Unknown modes fail closed with a validation/message rejection.

The normalized turn returns the actual `assistant_mode`.

## 9. Mobile settings

The Runtime OS assistant Settings panel now contains an `Assistant mode` selector:

```text
General chat
Agentic application development
Both
```

The choice persists in browser storage:

```text
hhs.production.assistant.mode
```

and is sent on every turn.

The active mode is visible in:

- the assistant header;
- assistant-turn metadata;
- the thread footer.

The default is `Both`.

## 10. Existing I007 UX remains

I008 preserves:

- customizable system instructions;
- mobile Copy;
- mobile Paste;
- natural-language response presentation;
- raw JSON hidden behind explicit inspection;
- user-controlled multimodal vector ingress;
- `vector_payload_auto_attached_to_prompt = false`.

## 11. Validation

Dependency-scoped I008 tests cover:

1. General Chat removes default HHS tools;
2. Agentic Application Development exposes governed tools;
3. Both retains conversational system semantics and tool capability;
4. unknown mode rejects before provider invocation;
5. native General Chat does not force repository retrieval;
6. native Both does not force repository retrieval for ordinary chat;
7. native Both activates repository retrieval for explicit development requests;
8. native General Chat completes an ordinary prompt-response turn without an agentic tool round;
9. developer-only native mode redirects unrelated chat;
10. REST accepts all three modes and rejects unknown modes;
11. mobile Settings exposes/persists all three choices;
12. Runtime OS source verification requires the mode selector.

## 12. Authority

Assistant mode controls **how language generation and governed tools are composed**, not who owns state.

No mode grants direct:

```text
VM81 mutation
Hash72 commit/mint
Hash216 mutation
repository mutation
deployment authority
filesystem authority
automatic vector disclosure
```

Those boundaries remain governed by their existing authoritative services.
