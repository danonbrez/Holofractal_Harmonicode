# 6. Lossless reversible VM81-to-64K model hydration

For a named source model checkpoint `W`, define the hydration operation:

```text
H = HydrateVM81_64K(W, manifest, architecture, operators, constraints)
```

Full model-hydration acceptance requires:

```text
ReverseExpand(H) = W
```

The equality SHALL include all source-significant model information:

- every checkpoint byte;
- file and shard ordering;
- tensor names;
- tensor shapes and strides;
- source data types and exact source encodings;
- tensor ordering and noncommutative operation ordering;
- tokenizer, vocabulary, merges, special-token identities, and prompt templates where applicable;
- scheduler, sampler, normalization, and architecture configuration;
- tied-weight relationships and aliases;
- model-specific metadata required for faithful execution;
- source license, provenance, repository revision, and file hashes.

The source checkpoint is an ingress witness. After successful hydration and reverse-expansion validation, the HHS hydrated capsule becomes the native runtime representation. The original source MAY remain as an archival witness but SHALL NOT be required as an unverified shadow authority.

Compression is not accepted when it is merely:

- lossy quantization;
- external checkpoint indexing;
- tensor sharding without reversible native reconstruction;
- an embedding that omits parameters;
- a pointer to a conventional model store;
- a partial adapter that cannot reconstruct the full admitted model state.

# 10. Multimodal invariant definition

A multimodal invariant is a typed relation, identity, topology, constraint, or executable transformation structure that remains valid across at least two distinct representations, modalities, models, states, or execution paths.

For modality projections `P_m`, an invariant candidate `I` SHALL satisfy:

```text
Validate_m(P_m(I), context_m) = true
```

for every declared modality `m` in its scope.

Examples include:

- object identity across text, image, video, audio, 3D, and simulation;
- geometry and topology;
- physical constants and conservation relations;
- character identity, rig, pose, and motion phase;
- camera, lighting, material, and occlusion relations;
- narrative and storyboard state;
- operation dependencies;
- parameter symmetries and reusable transformation circuits;
- Hash72 lineage and Hash216 continuation topology.

An invariant SHALL NOT be admitted solely because it correlates statistically in one dataset. It SHALL survive declared positive, negative, cross-modal, forward, inverse, replay, and mutation tests.

# 11. Computation-compression law

For a requested computation `C`, the runtime SHALL seek a decomposition:

```text
C = I ∘ Delta
```

where:

- `I` is the largest compatible validated invariant/retrieved continuation nucleus;
- `Delta` is the smallest dependency-complete unresolved transformation frontier.

The target cost is:

```text
Cost(C)
≈ Retrieve(I)
+ VerifyCompatibility(I)
+ Compute(Delta)
+ Validate(I ∘ Delta)
```

not repeated full recomputation of `I`.

No cache hit bypasses current constraints, VM81 admission, new Hash72 receipt creation, or post-receipt Hash216 archival.

# 12. Retrieval-augmented generation

A hydrated generation request SHALL follow:

```text
storyboard / prompt / source image / physics profile
→ current hydrated state
→ Hash216 candidate retrieval
→ exact typed compatibility rerank
→ ordered transformation composition
→ sparse novel-frontier inference
→ cumulative validation
→ VM81 admission
→ new Hash72 receipt
→ new Hash216 continuation
```

The runtime SHALL distinguish:

## 12.1 Exact continuation hit

Complete compatibility matches. The transformation may be replayed after current verification.

## 12.2 Compatible adaptation

A prior transformation matches most requirements but differs in declared parameters, object identity, camera, timing, environment, physics, or modality. The compatible topology is preserved and only its affected dependency frontier is recomputed.

## 12.3 Novel transition

No compatible record exists. A probabilistic model or other candidate producer performs the unresolved inference. The validated result becomes a new reusable continuation.

A vector-distance match alone SHALL NOT authorize reuse. Exact compatibility and dependency checks remain mandatory.

# 15. Progressive transitional-frame removal training

The initial video-training curriculum SHALL begin with complete motion sequences and progressively remove transitional frames.

For source sequence:

```text
S_0, S_1, ..., S_n
```

retain boundary/key states and reconstruct the missing sequence:

```text
S_i, [missing S_(i+1) ... S_(j-1)], S_j
```

The curriculum SHALL progress from:

1. isolated low-motion missing frames;
2. short continuous gaps;
3. alternating-frame removal;
4. motion-phase anchors only;
5. storyboard keyframes only;
6. initial state plus structured action instructions;
7. complete scene generation from storyboard, audio, and physical constraints.

Training acceptance SHALL evaluate, as applicable:

- exact endpoint closure;
- pixel and latent correspondence;
- object and character identity;
- geometry and depth;
- optical flow and motion phase;
- camera continuity;
- lighting and material continuity;
- collision, contact, and physical constraints;
- forward and inverse replay;
- deterministic reconstruction under recorded seed and configuration.

Successful reconstruction circuits SHALL become searchable Hash216 continuations.
