# 2. Purpose

Pass 189 turns the repository's existing modular backend, native projects, application registries, workflow factories, runtime services, visual tools, training layers, quantum layers, breadboard systems, language tooling, media systems, and future registered modules into one searchable template-object library.

The repository already contains substantial working functionality, including native projects, runtime applications, application-factory modules, workflow templates, visual tools, exact mathematics, VM81 components, compilers, interpreters, replay systems, media systems, games, vector stores, Word2Vec, NFT constraints, and Pass 186 native ABI work. The user must not need to know repository paths, pass numbers, internal package names, or implementation history to use them.

Every eligible module must become a template object that can be:

```text
SEARCHED
→ INSPECTED
→ PREVIEWED
→ INSTANTIATED
→ NESTED
→ CONNECTED
→ FORKED
→ EXTENDED
→ TESTED
→ COMPILED
→ EXPORTED
```

Similar and related modules must be grouped under logical modality sets and connected through a clear menu tree. The catalog must be generated from a thorough repository scan and maintained automatically as new modules are registered.

9. A template card, static screenshot, or menu label without real source, dependencies, tests, and callable behavior is not completion.

The scanner must distinguish:

# 5. Discovery methods

The scanner must use multiple signals rather than one filename convention:

1. Directory and file paths.
2. Build manifests, Makefiles, package files, and launcher scripts.
3. Explicit application registry entries.
4. Route registration and service composition.
5. Module catalogs and workflow catalogs.
6. CLI entry points.
7. C ABI exports and native bindings.
8. Python, JavaScript, TypeScript, shell, and C import graphs.
9. Tests that instantiate or invoke modules.
10. Pass contracts and implementation reports.
11. Registered capabilities, permissions, modalities, commands, and egress targets.
12. Existing Hash216/native binding registries and ownership declarations.

Every discovery run must emit:

```text
complete candidate inventory
classified executable inventory
excluded documentation/evidence inventory
unresolved candidate inventory
orphan and unreachable inventory
duplicate logical-module inventory
registry-vs-filesystem discrepancy inventory
scan root identity
Hash216 catalog identity
Hash72 scan receipt
```

No candidate may disappear silently. Unclassified items remain visible in an `UNRESOLVED` branch until reviewed.

# 9. Search requirements

The template explorer must support:

- exact title and ID search;
- path, filename, pass number, capability, and command search;
- aliases and synonyms;
- modality filters;
- maturity and implementation-status filters;
- input and output type filters;
- compatible-port search;
- egress-target search;
- dependency and reverse-dependency search;
- related-template search;
- license and permission filters;
- platform and environment filters;
- test-status and last-verified filters;
- native, Python, JavaScript, TypeScript, C, shell, and mixed-stack filters;
- full-text and semantic search over approved metadata and documentation;
- recently used, favorites, project-compatible, and recommended-by-graph views.

Semantic search is a discovery projection only. It may suggest candidates, but exact template identity, source, capability, and compatibility must be verified before materialization.

# 10. Similar and related module grouping

The catalog must calculate relationships using declared and observed evidence:

```text
same modality
same input type
same output type
same capability
same egress target
shared dependency
alternative implementation
adapter relationship
extends or supersedes
used together in a workflow
same native project family
same pass lineage
compatible with current project graph
```

The interface must distinguish:

- `RELATED` — semantically or operationally associated;
- `ALTERNATIVE` — serves a similar role;
- `REQUIRES` — hard dependency;
- `OPTIONAL_WITH` — optional enhancement;
- `ADAPTER_FOR` — type or protocol bridge;
- `EXTENDS` — additive capability;
- `SUPERSEDES` — newer authoritative replacement;
- `INCOMPATIBLE` — known conflict;
- `COMPOSED_IN` — used by a larger workflow.

Relationship generation may propose candidates automatically, but authoritative relationships require verified source/dependency evidence or explicit registration.

# 11. Template materialization

Selecting a template must create a real project or nested object through the application factory and Pass 187 composition authority.

Materialization must:

1. Show source root, status, dependencies, permissions, license, tests, and egress targets before creation.
2. Resolve deterministic dependency closure.
3. Detect cycles, conflicts, missing tools, and unavailable runtime capabilities.
4. Preserve source files and exact lexical identity.
5. Create project-scoped copies, references, forks, or live links according to explicit user choice.
6. Bind the new object to the current composition graph when requested.
7. Produce durable job IDs, checkpoints, cancellation, retry, and failure reasons.
8. Emit Hash216 identities and Hash72 receipts for admitted project mutation.
9. Permit source ZIP export independently of compilation.
10. Never fabricate successful native compilation, test, model availability, deployment, or runtime execution.

# 13. Future registration contract

Every future native project or modular application must register through a versioned manifest or adapter that supplies the template schema.

Registration must be additive and fail closed on:

- duplicate canonical ID;
- missing source root;
- path escape;
- invalid modality or port type;
- undeclared executable command;
- missing authority classification;
- dependency cycle;
- conflicting version;
- forged test status;
- unsupported license state.

A successful registration must automatically appear in search, relevant modality branches, related-module projections, API results, and materialization tests without manually editing multiple disconnected menus.

# 16. Required acceptance scenarios

Pass 189 cannot be marked complete until executable tests prove:

1. A cold repository scan discovers every current native-project root and registered runtime application.
2. Runtime Console, Calculator, Graph Projection, Breadboard, Receipt Inspector, and Replay Timeline appear in the catalog and correct menu branches.
3. Harmonicode language, interpreter, compiler artifact pipeline, VM81 native projects, symbolic runtime, application factory, vector store, Word2Vec, game, story reel, probability hydration, NFT constraints, and Pass 186 ABI families are classified.
4. AGI Training and Language Fine-Tuning branches exist and accurately distinguish executable, partial, and specification-only candidates.
5. Exact search by ID, title, path, capability, pass number, and egress target returns the correct canonical object.
6. Alias and semantic search produce candidates that are then identity-verified.
7. Compatible-port search finds valid Pass 187 connections and rejects incompatible ones.
8. Related-module grouping distinguishes dependency, alternative, adapter, extension, supersession, and incompatibility.
9. One template from every top-level modality branch materializes or is honestly rejected with an explicit non-executable status.
10. A Breadboard template is dragged into a project and connected to a compatible runtime object.
11. A quantum/tensor layer is nested into a computation workflow.
12. A language-processing or Word2Vec template is included in a language workflow.
13. A game or media template is instantiated and source ZIP export succeeds before compilation.
14. Duplicate IDs, path traversal, missing source, forged status, dependency cycles, and tampered manifests fail closed.
15. Adding a fixture future module causes automatic appearance in search and menu tree without hard-coded UI edits.
16. Removing or corrupting a registered source produces a visible registry discrepancy rather than silent omission.
17. Catalog, menu tree, relationships, and materialization plans reproduce identically after cold restart and replay.
18. Mobile touch, desktop pointer, and keyboard navigation open and materialize real templates.
19. Production-root acceptance verifies the Template Explorer is interactive and not a static home-page section.
