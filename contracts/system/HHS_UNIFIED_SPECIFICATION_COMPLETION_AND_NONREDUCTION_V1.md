# HHS unified specification completion and non-reduction contract v1

Status: proposed normative extension; does not supersede frozen runtime, exact algebra, or admission authority.

## Scope and identity
Every repository component, artifact, mathematical prompt, proof, dataset, visualization, standalone HTML, audio/physics experiment, code service, and production interface is part of one cumulative HHS/HARMONICODE lifecycle. Local standalone execution and deployed production execution differ in packaging, not intended architecture. Incomplete edges are integration work, not evidence of independent projects.

Until a fully functioning end-to-end beta has been verified and an explicit beta freeze authorized: do not fork the system for consolidation, prune branches/services, or archive historical files based on presumed redundancy. Retain provenance and development lineage.

## Non-reduction
For a newly supplied specification S, an existing implementation I, and a narrower established test/proof P:

- I satisfies P does not imply I satisfies S.
- Shared mathematical or observable properties do not imply typed, ordered, cell-addressed, phase-preserving equivalence.
- A description, filename, pass label, test scope, or index omission is not a binding upper limit on required implementation.
- More complex, simpler, or unintuitive constructors demanded by S remain implementation requirements unless contradicted by applicable frozen constraints; record and resolve actual conflicts.
- A proposed optimization is valid only with a typed ordered equivalence witness covering source identity, exact operators, constructor order, cell addresses, phase, provenance, invariants, input/output contracts, and observable behavior.

Verbatim supplied master tensor expressions and proofs are source specifications for executable portable optimization. Preserve lexical widths, noncommutative ordering, rational/symbolic operations and open obligations. A visual approximation or metadata-only receipt is not execution.

## Mandatory discovery and completion path
1. Establish current authoritative main, branch and source provenance.
2. Inspect AGENTS.md, README.md, REPOSITORY_INDEX.md, ARCHITECTURE.md, RUNTIME_FLOW.md, applicable pass contracts and restart record.
3. Traverse REPOSITORY_HASH216_DEPENDENCY_TREE.md and Lane 5 hydration graph/database; search code, native constructors, compiler paths, C/C++ ABI, tests, proofs, receipts, and historical implementations beyond names and indexes.
4. Enumerate requirements individually: inherited capability, incomplete implementation, missing integration, or genuinely new constructor. Scope tests/proofs only to what they establish.
5. Extend frozen layers by composition or compatible inheritance. Repair missing functionality and integration rather than abandoning the task.
6. Preserve the singleton VM81 admission and inherited Hash72/Hash216/replay authority. Lightweight portable Hash72-lite is a local execution form, not a second production mutation authority.
7. Validate applicable source-to-CI-to-merge-to-deployment-to-runtime behavior. Preserve failure codes and rejected candidate evidence. Never weaken a validator to force acceptance.
8. Report exactly what is implemented, tested, open and externally blocked with restartable evidence. An unresolved requirement remains an explicit task, not an implicitly waived one.

## Bypass-negative validation obligations
Gate coverage SHALL include a real Git rename of a protected file and verify both old and new paths are examined (for example, use --no-renames or --name-status with correct rename expansion). Include copies, deletion, alternate entrypoints, workflow path changes, missing/forged receipts, invalid phase/address/order, mismatched parent, and runtime rejection propagation. A green diff-scoped workflow alone is not proof of source-integrity closure.

A merged bypass creates two defects: the underlying source/integration violation and missing CI/deployment coverage. Repair both; never silence diagnostic error codes or replace runtime rejection with success.

## Integrated HTML / audiovisual example
The evolving system prototype preserves all particle, RGB-WB, ChaseCam, Liquid Light and media improvements. Hash72-lite is the required portable execution membrane. Brownian noise is the deterministic inaudible fallback analysis carrier when external PCM is absent. Physics, gradients and PCM/Brownian analysis derive from a common exact tick/phase clock; expensive rendering does not reduce physics time. Offline generation completes frames at physics-derived timestamps and buffers encoded media; streaming behavior must be measured rather than presumed. No current prototype claim establishes full native equivalence without test evidence.

## Acceptance evidence
- Requirement-to-service/constructor graph with explicit open gaps.
- Exact source/proof preservation and positive, negative, replay, rollback vectors.
- Actual rename/path-bypass negative test on a protected file.
- Runtime rejection and CI disagreement diagnosis, when relevant.
- Portable/production observable parity, signed admission evidence where applicable.
- Current-main artifact, receipt lineage, deployment identity and verified user-facing operation.
- Restart record with commit, branch, test commands, outcomes and remaining blockers.

No document, isolated test, or passing workflow alone attests to full implementation.
