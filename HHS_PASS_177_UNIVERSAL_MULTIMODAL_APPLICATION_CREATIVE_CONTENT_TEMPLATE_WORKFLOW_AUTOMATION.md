# 2. Normative language

The terms **SHALL**, **SHALL NOT**, **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are normative.

This contract authorizes a universal, extensible creation system. It does not claim that every conceivable environment, modality, codec, platform, store, device, or deployment provider is already implemented. An environment or modality becomes supported only through a registered and executed adapter with terminal evidence.

# 3. Append-only inheritance

Pass 177 SHALL inherit every compatible repository-visible contract, implementation, test, schema, compiler surface, API, ABI, Visual IDE workflow, deployment rule, evidence record, receipt, and correction through Pass 176 as a minimum foundation.

Pass 177 SHALL preserve:

- the frozen Pass 176 visual configuration and reliability requirements;
- Pass 175 virtual processor, VM81 admission, Hash72 commit, and Hash216 identity authority;
- Pass 174 canonical system-image inheritance;
- HARMONICODE source authority and exact symbolic semantics;
- source-byte, operand-order, parenthesization, lexical-width, and leading-zero identity;
- the natural-language assistant as a persistent IDE capability;
- project file tree, editor, preview, compiler, terminal, registry, history, multimodal ingress, and egress;
- the pre-pass and numbered-pass constraint lineage visible in the final application surface;
- incremental Git delivery and restartable authoritative-main closure;
- human-readable controls instead of raw JSON as the default experience;
- production deployment, observability, accessibility, security, and recovery requirements.

# 6. Required result

Pass 177 SHALL implement a creation environment that:

1. begins from a plain-language goal, visual template choice, existing project, folder, repository, or multimodal source set;
2. creates a complete editable project rather than a mockup;
3. supplies sensible files, assets, configuration, workflow, tests, build targets, and documentation;
4. supports source editing, visual editing, and natural-language assistance over one project model;
5. imports and creates text, code, documents, structured data, images, audio, video, animation, 3D, and binary assets through registered modality adapters;
6. validates dependencies and provisions declared toolchains through governed installers;
7. previews or renders the project in an appropriate sandbox or target simulator;
8. executes tests appropriate to the project family;
9. compiles or transforms the project for one or more verified target environments;
10. packages source, builds, assets, manifests, evidence, and receipts;
11. exports or deploys only through explicit authorized workflows;
12. resumes interrupted workflows from repository-visible and project-visible checkpoints;
13. remains usable by a person who does not understand VM81, Hash72, Hash216, or internal pass architecture;
14. retains full expert inspection and control for users who require it;
15. proves representative end-to-end creation across every required template family.

# 7. Universal support rule

“Any environment or modality” SHALL mean:

```text
any environment or modality represented by a registered adapter
whose schema, dependencies, capability checks, execution boundaries,
tests, packaging rules, and evidence requirements have been implemented
and verified on the active platform.
```

Unsupported requests SHALL produce a clear capability gap and implementation path. The system SHALL NOT pretend that changing a filename extension, generating a plan, or emitting placeholder metadata constitutes compilation or modality support.

# 18. Typed workflow graph

Every automation SHALL be represented as a versioned directed graph:

\[
\mathcal W=\langle N,E,I,O,C,R,P,H_{216}\rangle
\]

where:

- `N` is the ordered set of typed steps;
- `E` is the dependency edge set;
- `I` and `O` are typed workflow inputs and outputs;
- `C` is the constraint and capability set;
- `R` is retry, rollback, and recovery policy;
- `P` is permission and authority policy;
- `H216` is the workflow identity.

Every step SHALL declare:

- step identifier and version;
- human-readable purpose;
- typed inputs and outputs;
- source and target roots;
- dependency requirements;
- authority required;
- idempotency classification;
- timeout;
- cancellation behavior;
- retry policy;
- rollback or compensation behavior;
- logs and evidence;
- success and failure predicates.

# 19. Standard lifecycle graph

The canonical high-level lifecycle is:

```text
SELECT OR DESCRIBE GOAL
→ RESOLVE TEMPLATE AND TARGET CAPABILITIES
→ CREATE VERSIONED PROJECT
→ IMPORT OR GENERATE MULTIMODAL ASSETS
→ EDIT VISUALLY, IN SOURCE, OR THROUGH THE ASSISTANT
→ VALIDATE PROJECT, DEPENDENCIES, PERMISSIONS, AND CONSTRAINTS
→ PREVIEW OR RENDER
→ TEST
→ INTERPRET AND COMPILE FOR SELECTED TARGETS
→ VERIFY OUTPUTS
→ PACKAGE SOURCE, BUILDS, ASSETS, EVIDENCE, AND RECEIPTS
→ EXPORT, PUBLISH, OR EXPLICITLY AUTHORIZED DEPLOYMENT
```

Users MAY run one step, a selected subgraph, or the complete graph.

# 20. Restartability and checkpoints

Every mutating or expensive workflow SHALL persist checkpoints sufficient to resume from project-visible and repository-visible state.

A checkpoint SHALL include:

- workflow and project identity;
- completed steps;
- active step;
- source root;
- dependency state;
- environment capability state;
- produced artifacts;
- outstanding permissions;
- errors and retries;
- next action;
- rollback information;
- authoritative receipts where applicable.

An interrupted workflow SHALL resume, safely rerun an idempotent step, or roll back. It SHALL NOT depend on an agent retaining hidden scratch state.
