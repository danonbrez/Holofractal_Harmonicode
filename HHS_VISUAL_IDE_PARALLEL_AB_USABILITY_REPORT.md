# HHS Visual IDE Parallel A/B Usability Optimization Report

## 1. Scope

This report evaluates two visual-development-environment interaction models against the same executable local workflow backends.

- **Variant A — object-first baseline:** registered-object navigation, assistant thread, API controller, and inspector are separate primary surfaces.
- **Variant B — workflow-first candidate:** modality templates, an explicit five-stage plan, focused execution controls, artifact summaries, and progressively disclosed evidence are the primary surface.

The objective was not to replace Pass 161 object identity, nested panels, API control, diagnostics, or authority visibility. The objective was to keep those capabilities available while reducing the navigation cost imposed on ordinary application-development work.

## 2. Evidence classification

The trials used scripted interaction proxies in two browser processes launched in parallel for each workflow. Both variants received the same task definition and the same prevalidated executable backend result.

The workflow builders performed real local work:

1. generated source or data artifacts;
2. executed compile, schema, calculation, extraction, or geometry checks;
3. produced output files and SHA-256 identities;
4. returned successful local-validation results to both interface variants.

These results establish controlled usability and local artifact validation. They are **not** presented as recruited-human usability results and are **not** canonical VM81 mutation receipts.


### 2.1 Binary evidence storage policy

Screenshots and MP4s are generated by the reproducible `ux_lab` harness and published as the `visual-ide-ab-evidence` GitHub Actions artifact. They are not recommitted as binary history on every capture run. The repository stores the harness, metrics, SHA-256 manifest, completion receipt, and analysis; the CI artifact stores the generated PNG and MP4 files.

| Metric | Variant A | Variant B | B relative to A |
|---|---:|---:|---:|
| Successful workflows | 4/4 | 4/4 | Equal |
| Mean task actions | 8 | 4 | **50% fewer** |

| Mean scripted completion time | 4,410 ms | 2,689.75 ms | **39% faster** |
| Median scripted completion time | 4,403 ms | 2,684 ms | **39% faster** |

The timing includes fixed scripted pauses after each action. It is useful for comparing the two navigation models, not for predicting a human completion-time distribution.

## 6. Findings

### 6.1 Variant A strengths

- Registered objects and diagnostics are continuously visible.
- Raw response and receipt detail is easy to inspect.
- The layout supports expert object-level debugging without additional disclosure actions.
- Existing Pass 161 identity, inspector, API, and spatial surfaces are preserved.

### 6.2 Variant A usability costs

- The object registry, assistant, API controller, and inspector compete as equally primary surfaces.
- Successful application development requires repeated context switching even when the workflow is predictable.
- Raw JSON dominates the completion state and weakens the distinction between goal, next action, artifact, and evidence.
- A persistent 340-pixel inspector reduces the main work area before the user asks for advanced evidence.
- The interface identifies system objects well but does not identify the current development stage well.

### 6.3 Variant B strengths

- The workflow begins with an intended outcome rather than an object taxonomy.
- A five-stage strip makes progress and the next action explicit.
- The run console, artifact list, and evidence context remain associated with the active task.
- Advanced object controls remain available but no longer consume the default working width.
- Modality templates provide stable starting points without creating alternate runtime authority.
- The same successful backend result required half as many scripted actions and one quarter as many context switches.

### 6.4 Variant B issues found and resolved

- **Footer collision on long workflows:** repaired with internal workspace scrolling and explicit operation-strip clearance.
- **Potential template overload:** the recommended implementation uses a horizontally scrollable outcome strip rather than an always-expanded grid.
- **Advanced-data discoverability:** the global implementation adds explicit `Advanced Object Controls` and `Evidence` controls instead of silently hiding the inspector.
- **Keyboard discovery:** the global implementation adds a `Ctrl/Cmd+K` workflow/object command palette.

## 7. Accessibility observations

The evidence supports visible interaction findings but does not establish full accessibility compliance.

Observed improvements in the recommended default:

- stage state is represented by text as well as border color;
- controls retain 44-pixel minimum touch targets through the inherited style contract;
- advanced content is disclosed by explicit buttons with `aria-pressed` state;
- the command palette has dialog semantics and Escape dismissal;
- mobile mode controls expose Assistant, Workflows, Objects, and Evidence directly;
- reduced-motion behavior is preserved.

Remaining verification obligations:

- complete keyboard focus-order and focus-trap testing for the command palette;
- screen-reader announcement testing for stage transitions and assistant completion;
- automated and manual contrast checks across every shader/fallback profile;
- zoom, reflow, and large-text testing at 200–400%;
- touch testing on physical Android hardware.

## 8. Recommended global default

Promote **Workflow-First Progressive Disclosure** as the global human-facing default.

The default shall contain:

1. a command/search surface for workflows, objects, services, and commands;
2. an outcome-oriented modality template strip;
3. an explicit five-stage workflow indicator;
4. a focused assistant and execution surface;
5. persistent artifact and receipt identity;
6. advanced registered-object controls available on demand;
7. mobile mode controls for Assistant, Workflows, Objects, and Evidence;
8. no new mutation, receipt, or truth path.

The Pass 161 object registry, nested inspector, spatial object view, API controller, diagnostics, customizable faces, shaders, sprites, and receipts remain inherited functionality. The change is a default-presentation and workflow-orchestration optimization.

## 9. Global-default implementation

The recommended default is implemented additively through:

```text
applications/holofractal_harmonizer/src/workflow-templates.mjs
applications/holofractal_harmonizer/src/ux-default.mjs
applications/holofractal_harmonizer/src/ux-default.css
```

`index.html` loads the enhancement after the canonical Pass 161 browser runtime. The enhancement does not replace `browser.mjs`, `core.mjs`, the object registry, or the existing assistant API.

Key implementation decisions:

- the inspector is collapsed by default on desktop and restored through explicit evidence controls;
- workflow selection preloads the governed assistant prompt rather than executing automatically;
- stage completion is derived from user actions and admitted assistant-turn projection;
- selected workflow templates are persisted as workspace preferences only;
- object search and command search share one discoverable keyboard surface;
- footer clearance prevents primary actions from being obscured;
- advanced metadata remains available in nested panels.

## 10. Modality workflow templates

| Template | Outcome | Stages |
|---|---|---|
| Code & Runtime | Source, dependency-scoped tests, runtime evidence | Scope → Implement → Test → Inspect → Close |
| API & Automation | Governed callable API, schemas, failure handling | Contract → Route → Tools → Negative Tests → Receipt |
| Data & Analytics | Validated dataset, metrics, charts, reproducible report | Source → Quality → Compute → Visualize → Validate |
| Document & Knowledge | Preserved source, structured extraction, knowledge report | Ingest → Preserve → Extract → Relate → Report |
| Image & UI | Visual target, responsive implementation, capture evidence | Target → Explore → Build → Capture → QA |
| Audio & Video | Timeline, deterministic transforms, renders, playback evidence | Import → Analyze → Transform → Render → Playback |
| 3D & Spatial | Scene graph, registered objects, projection-only shaders | Scene → Objects → Materials → Simulate → Validate |
| Model & Agent | Provider contract, bounded tools, evaluation, ingress evidence | Provider → Policy → Tools → Evaluate → Admit |

Each template declares relevant object types and default panels while preserving the shared VM81, capability, Hash72, Hash216, persistence, and replay boundaries.
