# HHS / HARMONICODE — Frozen-Layer Preservation Contract

**Status:** Normative development and composition contract. This document does not independently certify the closure status of any layer or alter an inherited theorem, implementation, or receipt.

**Governing rule:** Extend by inheritance and composition, not by rewriting closed foundations.

An existing layer that has satisfied its authoritative closure, invariants, and admission contracts is frozen for purposes of higher-order feature development.

1. Treat frozen native mathematics, tensor geometry, runtime semantics, service contracts, and proof identities as authoritative dependencies.
2. Never infer that a missing higher-level capability implies missing or defective lower-level logic.
3. Inspect existing services, repository contracts, `AGENTS.md` instructions, and implementation evidence before proposing changes.
4. Implement new functionality through existing constructors, interfaces, composition boundaries, and Lane 5 hydration.
5. Preserve exact operator ordering, types, addresses, provenance, signed admission, VM81 execution, Hash72 receipts, and Hash216 transition history.
6. Verify the complete composition independently without modifying inherited proofs or falsifying unresolved constraints.
7. External libraries, training, harnesses, and optimization tools have no independent authority to mutate frozen canonical semantics.
8. A verified lower-layer defect must enter a separate, explicitly authorized repair process with regression evidence. It must not be silently bundled into a feature extension.

## Default decision

```text
Closed foundation + new requirement → higher-order extension
```

**Not:**

```text
Closed foundation + new requirement → foundational rewrite
```

## Closure requirement

```text
Inherited invariants preserved ∧ new composition admitted ∧ frozen implementation unchanged
```

## Authority

```text
Theorem → Lane 5 evaluation → VM81 commit → Hash72 receipt → Hash216 history
```

A successful extension adds capability without invalidating the foundation that makes it possible.

## Application and evidence boundary

- First establish the applicable layer's closure and ownership from authoritative repository evidence; do not designate an unverified layer frozen by assertion alone.
- When an extension cannot be admitted, record the failed constraint and composition boundary rather than revising inherited logic to force acceptance.
- Keep repair proposals, approvals, code changes, and regression witnesses separately traceable from higher-order extensions.
- Distinguish documentary adoption of this rule from executable enforcement and from evidence of a particular feature's admission.
- Apply in conjunction with [AGENTS.md](../../AGENTS.md), [ARCHITECTURE.md](../../ARCHITECTURE.md), and [REPOSITORY_INDEX.md](../../REPOSITORY_INDEX.md). Existing specific invariants and service contracts remain authoritative.
